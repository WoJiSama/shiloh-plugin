# B站 / 抖音视频搬运工具：设计与踩坑完整指南

> 来源：一套已稳定运行的生产实现（QQ bot 插件的媒体搬运子系统）的完整复盘。
> 本文剥离了所有 bot/QQ 框架相关的内容，只保留"输入链接 → 输出视频文件和元数据"这条独立链路需要的全部选型、设计和真实踩坑记录。
> 所有坑点均来自线上真实故障与修复，不是理论推测。

---

## 0. TL;DR 选型结论

| 平台 | 路线 | 不需要什么 |
| --- | --- | --- |
| B站 | **纯 HTTP + 官方 web 接口 + Range 并行下载** | 不需要浏览器、不需要 ffmpeg、不需要登录（除非要高清/会员内容） |
| 抖音 | **静态解析分享页（快路）+ puppeteer 渲染桌面页（兜底，当前实际主力）** | 不要逆向 a_bogus 签名算法 |
| 共用 | 单飞并发控制、短时 URL 不持久化、稳定 ID 做下载缓存键、全面降级 | — |

一句话架构：

```
识别链接 → 解析元数据 → 获取播放地址(短时有效) → 并行下载到临时文件 → 输出文件+元数据 → 清理
```

---

## 1. 整体流程设计

```
输入消息/文本
  → 正则识别链接（b23.tv / BV号 / ep号 / v.douyin.com / douyin.com / iesdouyin.com）
  → 构造统一"卡片"对象（平台、稳定ID、标题、作者、时长、封面、统计、metadata_status）
  → 元数据富化（B站 view API / 抖音分享页或浏览器）
  → 获取播放地址（短时有效，用完即弃，绝不持久化）
  → 下载（Range 分片并行、字节上限、超时、备选 CDN 回退）
  → 产出：视频文件（或图集图片）+ 结构化元数据
  → 临时文件清理（引用计数 + TTL）
```

核心设计原则（每条背后都有坑）：

1. **URL 是数据，不是身份**。播放地址几分钟就过期，幂等键/缓存键永远用稳定标识（BV号、aweme_id），永远不用临时 URL。
2. **媒体可以失败，信息不能丢**。视频拿不到时仍输出标题/作者/封面/页面链接 + 失败原因，不静默。
3. **同一作品被处理 N 次只下载一次**。按稳定 ID 复用下载产物。
4. **反爬目标站点的并发必须收敛**。宁可排队串行，不要并发触发风控。
5. **所有失败分类可见**。"需要登录"、"地区/版权限制"、"接口错误"分开说，不笼统报错。

## 2. B站实现

### 2.1 接口清单（全部公开 web 接口，无需逆向）

| 用途 | 接口 | 说明 |
| --- | --- | --- |
| 短链解析 | 直接 fetch `b23.tv/xxx`，跟重定向 | 落地页可能返回 412，但最终 URL 已含 BV 号 |
| 视频元数据 | `GET api.bilibili.com/x/web-interface/view?bvid=<BV号>` | 标题/UP主/时长/分P列表/封面/统计数据，免登录 |
| 番剧元数据 | `GET api.bilibili.com/pgc/view/web/season?ep_id=<ep号>` | 拿分集 cid |
| 播放地址（普通） | `GET api.bilibili.com/x/player/playurl?bvid=&cid=&qn=&fnval=0&fourk=0` | 返回 `data.durl` |
| 播放地址（番剧） | `GET api.bilibili.com/pgc/player/web/playurl?ep_id=&cid=&qn=&fnval=0&fourk=0` | 返回 `result.durl`（字段层级不同！） |
| 扫码登录（可选） | `passport.bilibili.com/x/passport-login/web/qrcode/generate` + `/poll` | 用于高清/会员内容 |

请求头必备：`User-Agent: Mozilla/5.0` + `Referer: https://www.bilibili.com/`。下载时同上，Cookie 仅授权请求带。

### 2.2 关键设计点

**`fnval=0` 是最重要的选型决策。** 它请求的是 FLV/MP4 旧格式，返回的 `durl` 是**音画合一的单文件直链**，下载即得完整 mp4。如果用 DASH（fnval=16）会拿到分离的音轨+视频流，必须再上 ffmpeg 合流。

**清晰度 qn 对照**（自动搬运用 qn=6 最低清，省带宽省风控）：

```
6=240P  16=360P  32=480P  64=720P  80=1080P  112=1080P+  116=1080P60  120=4K
匿名一般到 360P/480P；登录免费到 1080P；1080P+/4K 需要大会员
```

**多分P处理**：view API 返回 pages 数组（每 P 一个 cid），逐 P 请求播放地址，上限取 20 P。

**授权升级路径（可选）**：匿名请求 → 返回试看/需登录 → 用扫码登录保存的 Cookie 重试一次。Cookie 只存 `SESSDATA; bili_jct; DedeUserID` 三个值，文件权限 0600。

**缓存**：元数据内存缓存 30 分钟 / 100 条；播放地址**只做在途请求合并**（Promise 共享），落地结果不缓存——因为它短时有效。

### 2.3 B站坑点（全部真实踩过）

1. **CDN 直链必须带 Referer，否则 403。**
   bilivideo CDN 直链不带 `Referer: https://www.bilibili.com/` 实测 403，带了才 200。所以**绝不能把 durl 直接交给第三方下载器/播放器**，必须自己带 Referer 下载成本地文件再分发。

2. **b23.tv 短链落地页对服务器返回 412。**
   反爬页面状态，但重定向后的最终 URL 已含 BV 号。对策：先从最终 URL 提取 BV，再决定是否把非 2xx 当失败，不能一见 412 就抛错。

3. **单连接限速 ~1MB/s。**
   10.5MB 视频单流实测 10.6s，Range 分片 8 并发降到 2.5s（快一个数量级）。分片下载器设计见第 4 章。

4. **请求的 qn ≠ 实际返回的 qn。**
   请求 qn=6（240P）但视频最低只有 360P 时，接口会回落返回 quality=16，不报错也不强行提升。展示"实际清晰度"必须用返回值，别用请求值。

5. **番剧接口字段层级不同。**
   普通视频播放数据在 `payload.data`，番剧在 `payload.result`。早期只读 `data.durl`，番剧永远空数组且**静默失败**——不报错、不提示、就是没视频。

6. **试看片段陷阱（最重要的内容坑）。**
   番剧/会员视频匿名请求会正常返回 `is_preview=true` + 约 360 秒的试看 durl。只检查"durl 存在"就会把 6 分钟试看当正片搬运。必须识别 `is_preview`：要么跳过不下载，要么明确标注"仅提供约 X 分钟试看"。识别到试看后可用登录 Cookie 重试，仍是试看则放弃并说明。

7. **失败原因要分类。**
   code≠0 时按 message 区分"要求登录"、"地区/版权限制（港澳台/海外）"、"接口错误 N"，给用户的降级文案各不相同。

8. **授权 Cookie 的请求不能进共享缓存。**
   带会员 Cookie 的播放请求如果和匿名请求共享在途结果/缓存，等于把会员清晰度"权限穿透"给所有匿名命中者。授权请求走独立通道。

9. **扫码登录细节**：二维码 170 秒过期；poll 返回 code 86038 表示二维码已失效需重新生成；凭据文件 chmod 0600。

10. **backup_url 要用起来。**
    durl 条目带 `backup_url` 备选 CDN 列表，主地址下载失败时逐个回退。

11. **QQ 小程序卡片识别（如果输入源是 IM 消息）**：JSON payload 可能双包裹（`data` 是字符串、`data.data` 还是字符串），要三层兜底取；文本带 HTML 实体（`&amp;`、`\/`、`&#x2F;`）必须解码。

## 3. 抖音实现

### 3.1 双层架构

```
识别链接（域名校验白名单）
  → 快路：fetch 分享页 + 解析内嵌 JSON（移动 UA）
      成功 → 得到元数据 + play_url
      失败 → 记录失败时间，30 分钟内直接跳过快路（熔断）
  → 兜底：puppeteer 渲染桌面页（全局单飞）
      拦截 detail 接口响应 + 读 <video> 元素 + DOM/JSON-LD 补充
  → 下载 play_url / 图集图片
```

现实情况：**抖音 2026-09 改版后分享页不再内嵌数据，快路必然失败，浏览器兜底就是实际主力**。但快路保留着——哪天恢复了能省大量资源和时间（熔断机制让失败期每轮只多花 ~0.7s 判断）。

### 3.2 快路细节

- 移动 UA（`Mozilla/5.0 (Linux; Android 10; K)`）fetch 短链，跟随重定向到 `iesdouyin.com/share/video/<id>`。
- 页面 HTML 里的 `window._ROUTER_DATA = {...}` **不能 JSON.parse 整页**，用括号配平法截取那一段再 parse。
- 数据路径：`loaderData["video_(id)/page"].videoInfoRes.item_list[0]` → 描述/作者/时长/统计/封面/play_addr。
- 页面可能带 captcha/verify 标记：短超时（7s）+ 失败保留原始链接降级，不假设永远可抓。

### 3.3 浏览器兜底细节（每步都是踩坑换来的）

**共享浏览器实例**：`headless: "new"` + `--no-sandbox --disable-setuid-sandbox --disable-dev-shm-usage --disable-gpu`；闲置 10 分钟自动关闭，避免每次冷启动。断线自动重建。

**短链预解析**：先纯 HTTP manual redirect 跟最多 3 跳解析出 `/video/<id>`，**直接导航到桌面页** `www.douyin.com/video/<id>`。让浏览器先加载分享页再被客户端跳转会白耗 0.5–1.5s 还多一次导航。

**反检测补丁**（`evaluateOnNewDocument`）：

```js
navigator.webdriver  → undefined
navigator.languages  → ["zh-CN", "zh", "en"]
navigator.platform   → "Win32"
navigator.userAgentData → Chromium/Chrome 125, Windows, 非移动
window.chrome = window.chrome || { runtime: {} }
```
外加桌面 UA（Chrome 125 Windows）。**移动版分享页对无头浏览器直接返回"抱歉出错了"，必须走桌面页。**

**核心思路：不逆向签名，让页面自己算。** 抖音 web 接口需要 `a_bogus` 签名，算法随版本漂移追不过来。正确姿势：页面自己的 JS 会完成签名并请求 `/aweme/v1/web/aweme/detail/`，我们：

- 监听 response 事件，捕获 detail 接口的 JSON（校验 content-type 是 json）；
- 同时读 DOM 里 `<video>` 元素的 `src`/`currentSrc`；
- 两路互为备份，再加 `og:title`、`h1`、JSON-LD（补标题/时长/封面）兜底。

**请求拦截省流量**：页面不拦截会自己拉 MB 级媒体流。把 media/font 资源、`.woff/.ttf/.m4s/.ts/.mp4` 后缀、埋点路径（`webmssdk|mcs|slardar|tnc|collect|beacon|applog`、`/log/`）全部 abort——反正不需要页面真的播放。

**等待策略**：视频页等 `<video>` 挂载（≤10s）+ detail 响应（≤6s）；总超时 25s。等待失败不抛错，继续走 DOM 兜底提取。

**播放地址提取**：从 detail JSON 深找第一个可用的 `play_addr.url_list`（结构随版本漂移，深找比固定路径稳；`play_url` 字符串形如 `https://...mp4` 也可）。作品节点定位：deepFind 到"带 aweme_id 且有 desc 或 video 字段"的节点，从它取标题/作者/时长/封面——**不要全局取值**，页面数据里推荐流/评论区都是相似结构。

### 3.4 图集（图文作品）支持

- 识别 `/share/note/<id>` 或 `/note/<id>` URL（图文作品的"视频"是轮播图）。
- 图集来源：detail JSON 中"带 aweme_id 且自带 images 数组"的节点（优先）；DOM 兜底取轮播播放器容器内带图床标记的 `<img>`。
- **取图必须定位作品节点**：推荐流/评论区/贴片都带 images 数组，全局深挖会把别人的图收进来。
- **同一张图有多个 CDN 变体**：不同主机/签名的 URL 是同一张图，按图床对象 ID（URL 路径 `/tos-cn-xxx/<文件id>`）去重。
- **懒加载时机**：slider 的期望张数挂载即有，但每张 slide 的 img 逐张懒加载要 ~12s；播放器容器标记图 ~6s 全齐。凑齐判据用后者，凑齐即走。
- 图文作品不下载轮播视频（要的是图集本身），duration 置 0 让视频路径自然关闭。
- 上限：20 张/作品，超出截断并说明；单张 32MB / 60s 超时。

### 3.5 抖音坑点（全部真实踩过）

1. **play_url 短时有效，缓存它 = "视频已过期"。**
   早期把整张解析卡片缓存 15 分钟，里面的播放地址过期后再次使用就过期。对策：解析缓存压到 30 秒（只承担几乎同时到达的请求合并）；**任何持久化存储（数据库/日志/缓存）永不保存 play_url**，只在当次处理内存里用。

2. **分享页 SSR 说没就没。**
   2026-09 改版后分享页不再内嵌 `_ROUTER_DATA`，静态解析从"偶尔失败"变"必然失败"。对策：失败后 **30 分钟熔断**（期间直接跳过快路，成功一次自动恢复）；失败立刻转浏览器兜底且告警不静默。**做抖音要有"任何静态解析路径随时会死"的心理预期和监控。**

3. **移动页对无头浏览器返回"抱歉出错了"。** 必须桌面页 + 反检测补丁（见 3.3）。

4. **并发开多个抖音页面会触发反爬，且是"静默"惩罚。**
   两个调用方几乎同时各开一个页面时，部分页面就是拿不到数据——不报错、不封禁，就是空结果。对策：**全局单飞**——整个进程同一时刻只开一个抖音页面，其余排队；成功结果缓存 60s 共享；失败不缓存可立即重试。另外"预刷新"和"富化"两条路径同时到达时必须合并成同一个在途请求，否则双开浏览器正好踩这个坑。

5. **别逆向 a_bogus 签名。** 算法随版本漂移；让页面自己的 JS 算，从网络响应和 video 元素截取。

6. **短链别让浏览器去跳**（省 0.5–1.5s），见 3.3。

7. **页面自播的视频流是纯浪费**，必须请求拦截（见 3.3）。

8. **图集取图要定位作品节点 + 按图床对象 ID 去重**（见 3.4）。

9. **图集懒加载时机别傻等**（见 3.4）。

10. **duration 有毫秒和秒两种口径**，不同接口不一样，按阈值折算（>36000 或 >10000 视为毫秒除以 1000）。

11. **域名白名单硬校验。** 提取到的 URL 必须落在 `v.douyin.com` / `*.douyin.com` / `*.iesdouyin.com`，防止构造消息把任意 URL 注入下载器。

12. **分享页有 captcha/verify 标记**：短超时 + 失败保留原始链接降级。

13. **下载时带 Referer**（`https://www.douyin.com/` 或页面 URL）+ 移动 UA。抖音 CDN 通常不限速，但走统一分片下载器无害（支持 Range 就并发）。

## 4. 共用工程组件

### 4.1 并行分片下载器

```
首请求: Range: bytes=0-262143  (256KB，故意小，串行成本 ~0.25s，兼做能力探测)
  ├─ 返回 206 → 从 content-range 解析总大小
  │     ├─ 总大小 > 上限(512MB) → 直接抛错，不发后续请求
  │     └─ 其余按 2MB 分片、8 并发(上限16)拉取，写入同一文件对应偏移
  └─ 返回 200 → 不支持 Range / 小文件：这条响应直接单流落盘，不再发新请求
```

要点：
- **不多发探测请求**——首片就是真数据，任何路径下媒体请求至少 1 次。
- 单个分片失败自动重试一次，再失败整体抛错。
- 分片长度严格校验（期望 vs 实得，不符即失败），防 CDN 返回截断内容。
- 总量硬上限 + 下载总超时（10 分钟），超限即弃不留半截文件。
- 下载到临时文件（`tmpdir + 平台子目录 + 随机名`），失败/超限时 finally 里删除。

### 4.2 缓存与单飞策略（三个层次）

| 层 | 对象 | TTL | 失败处理 |
| --- | --- | --- | --- |
| 元数据缓存 | B站 view 结果 / 抖音解析卡片 | B站 30min；抖音仅 30s（卡片含短时 URL） | 失败不缓存，可立即重试 |
| 在途合并（single-flight） | 同 key 并发请求共享同一 Promise | 无（请求结束即删） | 异常传播给所有等待者 |
| 单飞解析器（反爬站专用） | 抖音浏览器解析 | 成功 60s；失败不缓存 | 全局串行队列排队 |

通用规则：**真值结果按 TTL 缓存，null/异常结果绝不缓存**——失败后下次调用立即重试，不让一次抖动惩罚整个 TTL 周期。

### 4.3 下载产物复用（多任务场景）

如果同一作品会被多次处理（比如搬运到多个目标），用"产物仓库"模式：

- key = `平台:稳定ID:分P:清晰度`（如 `bilibili:BV1xxx:38547:c6`、`douyin:766xxx:lowest`）。**绝不把临时播放 URL 放进 key。**
- `acquire(key, producer)`：同 key 共享进行中的下载和已落地文件，引用计数归零后按 TTL（120s）延迟清理，空闲容量上限（如 8 个文件 / 512MB）超限淘汰最旧。
- 失败立即逐出，不缓存失败产物。

### 4.4 降级与上限

- **上限**：视频 ≤30 分钟且 ≤512MB 才下载本体；超过只输出元数据 + 页面链接 + 说明（"视频超过30分钟，未附带视频本体"）。
- **降级链**：元数据刷新失败 → 用首次识别时的卡片快照；播放地址拿不到 → 输出信息 + 失败原因（登录/版权/接口错误分类）；下载失败 → 同样只输出信息。**任何一层失败都不能让整体静默无输出。**
- **边界检查**：时长判断在请求播放地址**之前**（超长视频不触发下载）。

### 4.5 工程层坑点

1. **用 `tempFiles.length` 判断下载成功会误报。** 产物仓库工作时文件在 lease 里不在 tempFiles，判断要检查实际的产出对象是否存在。
2. **同一作品多任务重复下载**是默认会发生的事（各任务独立解析、独立下载），产物复用层要从第一天设计，后补侵入性大。
3. **临时文件泄漏**：所有下载路径的 finally 里都要清理失败文件；成功文件用引用计数 + TTL 统一回收，别指望调用方记得删。
4. **缓存键污染**：授权/非授权、不同清晰度的请求如果共享缓存 key 会互相污染（见 B站坑点 8）。

## 6. 最小可行实现路径

不需要一次做全，按这个顺序加：

1. **第一版（能跑）**：正则识别链接 → B站 view API + playurl(fnval=0) / 抖音分享页静态解析 → 带 Referer 单流下载 → 输出 mp4。抖音部分第一版可以只做浏览器方案（静态快路反正当前是死的，但要把熔断+兜底结构留好）。
2. **第二步（能用）**：并行分片下载器、失败原因分类降级、30min/512MB 上限、临时文件清理、超时控制。
3. **第三步（稳）**：产物复用、单飞解析器、分段耗时日志（`refresh/playback/download` 各一段毫秒数——没有这个日志，一半的坑根本发现不了）。
4. **第四步（可选）**：B站扫码登录 + 高清、图集支持。

**验收方法**：离线单测通过不算数（生产实现当年离线全过、线上照样丢）。必须拿真实链接端到端跑：普通视频、多 P、番剧、会员试看、图文图集、失效链接、超长视频，每类至少一条真实样本。

## 7. 踩坑速查表（症状 → 根因 → 对策）

| 症状 | 根因 | 对策 |
| --- | --- | --- |
| B站下载 403 | CDN 直链缺 Referer | 请求带 `Referer: https://www.bilibili.com/` |
| B站短链解析失败但浏览器能开 | 落地页 412 反爬 | 从重定向最终 URL 提取 BV，非 2xx 不必然算失败 |
| B站下载只有 ~1MB/s | 单连接限速 | Range 分片并行 |
| 番剧永远没视频且不报错 | 播放数据在 `result` 不在 `data` | 按 ep 请求切字段层级 |
| 搬出来只有 6 分钟片段 | 匿名返回的是 is_preview 试看 | 检查 `is_preview`，试看不下载或标注 |
| 清晰度显示和实际不符 | qn 请求≠返回（回落） | 用返回的 quality 展示 |
| 抖音二次搬运"视频已过期" | 缓存/持久化了短时 play_url | 缓存≤30s，任何持久化不存 play_url |
| 抖音静态解析一直失败 | 改版后分享页无 SSR 数据 | 30min 熔断 + 浏览器兜底为常态 |
| 无头浏览器拿到"抱歉出错了" | 移动页识别无头 | 桌面页 + stealth 补丁 |
| 浏览器解析时好时坏、部分空结果 | 并发多页面触发静默反爬 | 全局单飞 + 在途合并 |
| 图集混入不相关的图 | 全局深挖 images | 定位带 aweme_id 的作品节点 |
| 图集重复发同一张图 | 同图多 CDN 变体 | 按图床对象 ID（tos-cn 路径）去重 |
| 图集等待超过 10s | 等 slider 懒加载 img | 用播放器容器标记图凑齐即走（~6s） |
| 时长有时差 1000 倍 | duration 毫秒/秒双口径 | 阈值折算 |
| 同一视频搬 N 次下载 N 次 | 无产物复用 | 稳定 ID 做 key 的产物仓库 |
| 会员清晰度泄漏给匿名请求 | 授权结果进了共享缓存 | 授权请求独立通道 |

## 附录：如果以后要把文件发到 IM/聊天平台

虽然本文按独立工具写，这几点是接入任何 IM 发送时的真实教训，提前知道能省很多排查时间：

1. **发送方（IM 网关/协议端）自己去拉 B站/抖音直链会 403 或过期**——永远先下载成本地文件再交给发送层。
2. **大文件以 base64 内联会撑爆 IM 网关的 WebSocket**，协议端还可能把 base64 改写成它自己的本地路径导致发送失败。优先走"发送方能访问的共享目录 + 文件路径引用"方案。
3. **"发出去了但没拿到回执"的场景绝不能自动重试**——重试就是重复刷屏。宁可保留失败状态待查。
4. **去重/幂等键必须包含目标会话**（如 `平台:目标:消息id`），绝不能用 URL 全局去重——同一个链接发给两个目标就该处理两次。
