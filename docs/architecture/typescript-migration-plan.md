# JavaScript → TypeScript 分阶段迁移计划

日期：2026-10-13。状态：计划已制定，迁移尚未开始。

迁移前基线：`a93265cd94e2307504dad11d26351cf954cfc071`，已提交并推送至 `origin/main`（WoJiSama/shiloh-plugin）。此次基线包含原有 15 个未推送提交及本轮积累的控制台、配置、生图、消息投递改动。

## 1. 目标和范围

目标是把我们维护的业务实现逐步改为严格类型的 TypeScript，同时理清模块边界、保留当前功能，并让每个阶段都有单测和可回滚的运行包。不能通过批量改后缀、添加大量 `any` 或新增 TS 文件稀释旧 JS 占比来认定完成。

- 后端继续 Node.js + ESM；控制台继续 Vue 3 + TS。控制台和机器人保持两个运行进程。
- 采用模块化单体：一个仓库、一个发布根，按功能域和职责分层。现有 standalone 入口继续兼容，本次迁移不强制物理拆成多插件或微服务。
- 最终第一方业务实现全部 TS；必要的 `.js` 引导入口、旧路径转导出及用户自定义 JS 工具/骰子规则列明兼容例外。
- 新核心模块直接使用 TS；尚未迁移的 JS 按切片补 JSDoc/局部 `checkJs`，不要求第一天检查整个旧仓库。
- 去锅巴化与类型迁移使用同一份配置契约；保留旧锅巴导出兼容，不同时维护两套业务规则。
- 语言迁移默认保持行为。结构抽取、类型迁移和行为修复分开提交；修复已有缺陷时先增加失败回归用例，再修改实现。

本计划替代 [旧蓝图](../refactor-blueprint.md) 中关于本次迁移顺序和物理多插件拆分的安排；旧文档的历史完成记录仍然保留。消息投递不变量沿用 [消息管道设计](message-pipeline.md)。

## 3. 目标结构和调用规则

下面是目标目录示意，阶段实施时逐切片落地；当前仓库尚不存在这些 TS 实现。

```text
src/
  contracts/                 # 共用 DTO、错误、回执、标识和端口
  modules/<业务域>/
    domain/                  # 纯策略、值对象、状态转移
    application/             # 用例与编排，依赖 domain 和端口
    infrastructure/          # provider、数据库、文件等端口实现
  adapters/                  # QQ/Yunzai、HTTP、旧 JS 能力接入
  bootstrap/                 # 依赖装配、生命周期、入口注册
dist/backend/                # 编译后的 JS，运行包生成，不手改
index.js / apps/*.js          # 宿主兼容引导和旧命令入口
console/frontend/            # 现有 Vue + TS，独立构建
```

- QQ/HTTP 入口把外部数据校验成 DTO，再调用用例；用例调用纯策略及显式端口。平台对象只在适配层转换。
- 领域层不依赖 Yunzai、Koa、Redis、provider SDK、磁盘或全局对象。基础设施实现端口，装配入口负责注入。
- 新服务不接收完整 `ExamplePlugin`/`host`、带方法的 Yunzai `e` 或 `pluginBridge.instance`。旧 JS 适配器提供所需能力；桥只转换数据和调用能力，不复制业务逻辑。
- 同域可以直接调用；跨域立即需要结果时使用公开服务接口，独立后续动作使用事件，需重启恢复的长任务使用持久化 job。事件不能代替需要可靠提交的任务记录。
- 跨进程共享的是可序列化协议和有版本的配置/任务，不是内存对象或隐式共享单例。

首批契约：`ProviderId`、模型标识、展示名称分别定义；`ImageRequest/ImageResult`、`AppError`、`DeliveryReceipt`、`ConfigSnapshot`、`ConversationContext`、`TurnSession`、持久任务 DTO；端口包括 `ModelGateway`、`ReplyPort`、`ConfigPort`、`TaskStore`、`Clock`、身份目录和资源存储。

TypeScript 只检查代码之间的约定。HTTP/provider 响应、配置文件、工具参数、Redis/job 记录均从 `unknown` 开始，做运行时校验；验证失败返回有来源的错误，不用类型断言把数据变成「可信」。

## 4. 编译、混合运行和发布约束

- 后端使用独立 `tsconfig.backend.json`，建议 `module/moduleResolution: NodeNext`、`target: ES2022`、`strict`、`noEmitOnError`、`verbatimModuleSyntax`；新模块启用 `noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`。
- TS 源码使用显式 `.js` 相对 import，编译后能由 Node ESM 正常解析。前端继续自己的 `Bundler`/`noEmit` 配置，不复制前端 tsconfig 给后端。
- 后端运行正式编译后的 JS。不能依赖 Node 原生移除类型作为正式发布路线，也不能让 `.js` 宿主入口直接 import `src/*.ts`。
- 旧 JS 与 TS 按模块共存。必要 `allowJs` 仅限桥接清单；新的严格检查不能靠吸入整个 legacy 仓库、通配 `any` 声明或全局关闭错误来通过。
- 当前根 `index.js` 和 standalone loader 只扫描 `.js`；保留命令名、插件导出形态、监听优先级和旧路径 wrappers。自定义 `.js/.mjs/.cjs` 工具继续可加载。
- 资源、配置和 data 路径使用装配时注入的 `pluginRoot`/资源根。不得让 `src → dist` 目录变化改变 YAML、模板、图片或宿主依赖的定位；专门测试不同 cwd 和真实宿主目录布局。
- 本地 Node 为 `v24.14.1`；阶段 1 读取实际线上及 standalone 的 Node 版本，确定支持范围并写入测试环境。本计划没有据此假定线上也是 Node 24。
- 阶段 1 就要接通构建与更新路径：CI/构建环境安装含开发依赖的锁定依赖，生成产物；生产运行无需安装 TS 编译器。现有部署脚本、standalone 发布、`#bl更新` 不能只 pull 源码而遗漏 dist。
- 发布包包含后端编译 JS、仍在使用的旧 JS/入口、前端构建、静态资源和 manifest；manifest 记录 commit、Node/编译器版本、锁文件 hash、文件 hash。从干净 commit 构建，运行文件可追溯。
- 安装一个完整且预检通过的发布包后再切换服务；不在运行中逐文件覆盖编译产物。清理旧输出按 manifest，保护 config/data，并在切换前停止接收新长任务、等待/登记在途任务。

## 6. 每阶段的硬性测试门槛

**相关单测未通过，该阶段不算完成，也不进入下一阶段。** 每个子阶段使用相同门槛；最后还要做父阶段整体回归。

1. **类型检查**：新增/迁移模块严格检查通过；关键契约的错误输入有编译负例，防止类型退化为 `any`。`@ts-ignore`、不受限断言和宽泛 `any` 必须移除或登记具体原因，不能作为完成迁移的办法。
2. **相关业务单测**：上表正常、失败、边界、权限、并发/状态场景全部通过；采用 fake clock、fake Redis、provider/OneBot fixtures 和临时目录，默认无付费请求或真实群发送。关键分支按用例清单全部覆盖，不只测 happy path 或照抄实现。
3. **编译产物验证**：独立构建后加载 emitted ESM，并从 QQ/HTTP/宿主适配入口验证导出、路径和行为；既检查源码，也验证将发布的 JS。只在开发 TS runner 上通过不能作为加载证明。
4. **依赖边界**：自动检查领域/用例层不能 import 平台、完整插件、全局 bridge；检查业务层无未登记全局访问，迁移后旧业务实现删除，仅保留薄适配。
5. **整体回归**：阶段结束跑聚合后端全量单测、前端类型检查/单测/构建。阶段 1 必须让聚合命令同时发现 legacy JS 与新 TS 测试，之后每阶段使用同一入口。
6. **证据与跳过项**：记录 commit、命令、环境、测试发现数、通过/失败/跳过、覆盖的迁移模块、产物 hash 和结果。新增的相关核心测试 0 失败、0 跳过；既有环境集成跳过单列原因和补验方式，不能把「运行了部分测试」写成「全量全绿」。
7. **发布与回滚**：阶段准备完成需有可回滚 artifact 和配置/job 兼容验证。将本地验收、推送、线上安装、线上观察分别记状态；部署后必须验收两服务、插件清单、命令/API、启动/业务错误和在途任务。涉及真实 provider/群发的验收单列，单测通过不等于上游实际遵守画幅等协议。

目前可用的验证命令：


阶段 1 **计划新增，当前尚不可直接执行**的统一入口：

## 7. 已知风险与必须补齐的回归

| 已知问题/风险 | 归属与处理要求 |
| --- | --- |
| 图片尺寸解析返回对象，但宽/高可能为 0；控制台目前只检查对象是否存在 | 阶段 3 补输出为零尺寸/损坏图片用例并修复；本轮基线未解决 |
| 出站审查仅读取 `params.message`，合并转发 `params.messages[].data.content` 未覆盖 | 阶段 5 补转发及混合 segment 审查用例并修复；本轮基线未解决，若当前继续启用审查需优先独立修复 |
| 第三方 Grok 服务可能忽略 9:16 等参数，返回正方形 | 阶段 3 验证参数契约与实际输出，明确渠道/模型/尺寸；不能仅通过类型检查宣称上游已修复 |
| 全插件 host、`pluginBridge` 和宿主聚合 import 使单测绑运行目录 | 阶段 1/2 隔离宿主；阶段 6/7 消除业务调用点，不将旧聚合 import 搬进 TS |
| 配置多种写入方式、两个进程生效时机不同 | 阶段 4 统一 revision/并发协调/原子写与跨进程刷新；旧字段不能静默丢弃 |
| 部分测试使用源码抽取，重构后易测到替身或漏发现 TS 用例 | 迁移相应模块时改正式 import；阶段 1 接通完整测试发现，阶段 8 清零源码抽取测试 |
| 当前部署同步工作目录，缺少后端产物/前端完整构建门槛 | 阶段 1 为混合运行补构建/安装；阶段 8 完成全仓可重现发布，避免旧 artifact 残留 |
| UI chunk 体积告警 | 阶段 7 根据页面依赖做路由/模块拆分并实测；与后端语言完成度分开报告 |

本计划没有通过检查清单宣称这些问题已修复。阶段执行时以新增回归及真实结果更新状态；阻塞当前使用的缺陷可以先做独立小修复，再合入迁移基线。
