# 海龟汤全面修复交付记录

对应 [设计审查](turtle-soup-design-review-2026-10-19.md) 中的生成、坏汤回收、主持判胜、并发存储、游戏流程和管理配置问题。用户授权“全部修复”后完成本地实现；没有执行提交、推送、部署或生产数据修复。

## 生成与失败候选

出题、修题和失败恢复共用一条准入链路：本地结构与难度/重复检查 → 可玩性 → 逻辑 → 问答推演 → 待审。管理员确认后才进入投放池。每版记录原文、内容哈希、问题和审核；修稿推进到新版本，原稿的审核不能证明修稿合格。

- JSON 或审核字段异常、超时和接口故障：保留失败阶段、原始响应、已有稿件和调用次数，允许从已有证据继续处理。同阶段有限重试并短暂退避，超时会取消底层请求。
- 可修复的逻辑、线索、提示等内容问题：最多两轮修稿，每版重新检查全部准入条件。
- 明确不可修复或机制重复：立即停止后续模型调用，保留教训，不提供继续恢复入口；后续技术错误不能绕过这一结论。
- 历史 `rejected.jsonl`：按内容生成稳定候选 ID，兼容导入回收列表。缺少提示等可补全内容先修复，再完整审核；重复恢复已入库候选返回同一个题目。
- 自动补货分别计算可玩鲜汤和待审积压。待审达到上限暂停，小游戏关闭时不自动补货。机器人与控制台共用跨进程生成锁。

生成提示要求固定事实、因果自洽、题面诚实、可发现的提问入口、必需判胜点和三条递进提示，并参考题材、难度和核心机制的多样性。语义审题会与相近旧题比较机制；文本重复检查仍作为独立保护。问答推演属于模型审题证据，并未运行一次真实玩家主持对局。

## 坏汤重新利用与评价

后台对原题发起修复会创建新的 pending 版本，保留家族与父题关联。旧题、旧评分和旧局记录保留；新版本不复制旧分数。批准新版时原子停用同家族旧投放版本；不能用旧版审批反向替换正在投放的更新版本，旧版已经开始的游戏仍能正常收局。

同家族继承已曝光的群与玩家，包括正在进行的游戏、中途加入和已投降玩家。修稿、更换文字不会把已知答案的人当成新玩家；重启恢复旧会话后也能立即获得旧局曝光记录。

玩家评分绑定 `playId`，允许揭晓或换汤后直接开始新局，并在原评分窗口内补评。可使用：

```text
.游戏 海龟汤 换汤 原因
.游戏 海龟汤 评分 上一局 2 线索 缺少合理的提问入口
.游戏 海龟汤 评分 pl_局号 4 提示 提示梯度合适
```

评价区分逻辑、线索、提示、主持、难度、题材和技术原因。每题按独立玩家最新一票汇总；至少三位独立玩家均分低于 3 时，暂停投放并转待审复核。管理员分数与理由独立保存，低分不能只留一个数字。换汤原因与有限问答/猜测轨迹可用于复盘，不自动折算低分。

生成质量例证只采纳最新独立内容类评价；主持故障、接口异常、难度偏好和题材喜好保留用于诊断，不进入坏题内容样本。无明细的历史总分不作为内容质量证据。

## 主持和对局

- 主持收到汤面、汤底与固定事实，允许“无法确定”，避免把未说明当否定。
- 每次猜底都经过事实核验。关键点使用稳定 ID，覆盖和矛盾条目必须有效、去重；必需点完整且无矛盾才可获胜。字面相似度不再直接判胜。
- 模型工作在群状态锁外进行；结果落地核对局次、playId 和 revision，结束/换汤会取消旧请求。主持超时、响应异常不消耗猜底冷却和失败次数。
- 选汤菜单与随机开局共用最低曝光优先策略；中途加入检查同家族曝光并补发已用提示。提示有间隔限制。
- 最后一位玩家投降后按人数收局，私发失败不使游戏停留在零人进行中。
- MVP 基于实际问答/猜测证据异步评选，更新指定旧局，揭晓和下一局不等候它。

## 存储与管理端

跨进程锁保护完整的读取、修改和写入。事务以全状态 journal 作为提交点，再导出 `puzzles.json`、`plays.json`、`sessions.json`、`candidates.json`，读取通过 journal/revision 防止半份更新。进程锁绑定 PID 与启动身份，恢复遗留锁而不抢占活着的长请求。

评分明细和题目汇总在同一事务中写入。模型重审只合并当前内容的审核结果，不覆盖等待期间的新评分或状态。若内容已改变，则拒绝过期审核。事务提交后的导出或清锁错误不再被当作业务提交失败；保留 journal 供读取，后续写入前先完成恢复，恢复仍失败则阻止新事务。

控制台提供候选回收、失败阶段、版本对照、当前审核、投放历史、反馈分类、鲜汤/待审库存、完局和提示等诊断统计。生成任务在开始等待前保留任务 ID，实时展示成功/失败/跳过；技术故障停止批次余下任务。当前内容无完整审核不能投放，审核失败会暂停现有投放。

配置页使用运行时的默认、钳制和 legacy 规则。总开关与海龟汤开关分别显示，必须同时开启才启用。只保存变化项到 `pluginSettings.miniGames.turtleSoup.*`，保留旧配置和无关字段；表单有效值 revision 与底层文件快照共同防止并发覆盖。插件根、宿主根和自定义数据目录统一解析。

## 默认预算与操作

| 参数 | 默认值/行为 |
| --- | --- |
| 可玩鲜汤目标 | 2 个不同家族 |
| 待审上限 | 未配置时取 4 与鲜汤目标两倍的较大值 |
| 单候选每次处理调用上限 | 18；可配置 4–100 |
| 自动补货共享调用上限 | 48 与“待审上限 × 单候选预算”中的较小值 |
| 手动批次共享调用上限 | 120 与“数量 × 单候选预算”中的较小值 |
| 内容修复 | 每次处理最多 2 轮，仍受共享预算约束 |
| 阶段请求超时 | 生成/审核 60 秒；主持 45 秒，均传递取消信号 |
| 评价窗口 / 提示间隔 | 5 分钟 / 15 秒 |

预算计数为本层模型调用，不包含通用网关内部的兼容重试，不能视为金额或 token 硬上限。人工重新处理候选会获得新的一次预算，累计调用数仍保留。

建议管理流程：查看待处理候选或低分原因 → 区分内容与主持/技术问题 → 对内容问题发起修复 → 对照新旧版本及当前审核 → 人工确认投放。旧题简单从“已出池”改回状态，也必须满足当前内容审核要求；已有旧格式活跃题保留兼容投放能力，后台明确标识需补审。
