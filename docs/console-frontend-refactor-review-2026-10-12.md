# bl-chat 控制台前端重构建议

审查日期：2026-10-12。依据：用户截图、当前工作区源码、当前 HTML 的离线浏览器复现。范围：分析与方案，不修改运行代码、不部署、不访问生产、不读取配置密钥。工作区已有未提交改动全部保留。

## 判断

控制台需要同时重构页面组织、表单交互、状态管理和工程边界。现有功能有价值：机器人实体、群收发统计、人设库/绑定、模型渠道、生图、风控、运行观测与语义记忆。应将这些能力组织成可操作的工作台，用消息管道页作为第一张完整示范页，逐步迁移。

## 截图能确认什么

- 一级侧栏加页内纵向目录占用两次横向空间，阅读入口与正文标题重复。
- 开关、标题、解释之间的视觉关系断裂，用户难以一眼确认自己在修改什么。
- 卡片横向铺满，字段窄而纵向拉长，形成大块空白；同屏信息缺少分组与节奏。
- 状态“干净”含义不清，应使用“无未保存修改”；配置是否保存与运行是否生效必须分别表达。
- 截图里的像素机器人占据表单阅读区，建议放回品牌位置或空状态，表单以任务内容为主。

**版本边界：** 当前源码的开关在同一个 label 内并使用 flex，数字字段为左右行。用当前 HTML 离线运行时，checkbox 为 16px，文字间距约 12px，未出现截图的远距离分离。因此截图错位的具体根因需要核对实际部署版本和浏览器计算样式；不能归结为当前某条 CSS。当前单文件模板也没有可见的构建版本标记，应增加发布版本/构建标识以方便以后核对。

## 页面组织

建议侧栏按管理员要做的事分组，机器人与群聊保留实体入口，避免为了导航归类而新增空页面。

| 分组 | 入口 | 页面重点 |
|---|---|---|
| 日常运营 | 机器人、群聊 | 谁离线、怎样恢复、服务哪些群；机器人详情关联人设和失败信息 |
| 机器人能力 | 人设、AI 模型、命令/骰子、语义记忆 | 说话方式、能力与模型配置；绑定关系尽量在实体详情中操作 |
| 消息与运行 | 消息与搬运、风控、运行观测 | 投递情况、失败原因、发送策略及异常定位 |
| 创作工具 | 生图工作台 | 生成、查看和使用作品；说说发布保持机器人上下文 |

统一一份页面元数据驱动路由、侧栏、搜索、面包屑和权限。现有 hash 地址保持可用。命令/记忆 iframe 先保留代理与认证，原生页面准备好后逐页替换。

## 消息与搬运示范页

### 首轮：重做配置体验

顶部只放页名、用途、保存状态和动作。页内使用横向任务分区：可靠管道、平台授权、健康报告。每个开关把名称、解释与操作放在同一行/块内；小屏自然堆叠。

- **可靠管道：** 前面展示启用与自动搬运两个核心开关。并发、尝试次数、保留时长、缓存和目录分成有意义的小组；高级项折叠，避免第一次进入就看到所有实现参数。
- **平台授权：** B站、YouTube 分开表达用途。B站高清命令开关不控制自动搬运；试看授权复试是另一项能力。YouTube 凭据显示已配置状态，通过修改动作输入新值。
- **健康报告：** 目标管理群、启用、周期放在一起，明确下次周期生效。首轮不新增“发送测试报告”这种有真实群消息副作用的动作。
- **数值：** 单位放在输入旁；字段名可以使用易读文案，但要保留实际语义，例如“交付状态保留”不能写成“视频保留”。范围和关联校验在输入处反馈。
- **保存：** 显示变更数、保存中/失败/成功与放弃修改；变更改回原值应清脏。切换分区保留草稿，离开页面可继续编辑、明确丢弃或保存。保存期间的新编辑不能被响应覆盖。

布局建立统一内容宽度，建议正文最大宽度约 1120–1280px；配置区以可阅读宽度为准，在宽屏对相关短字段做两列分组，不将一张空卡片拉满。页面顶部标题与卡片标题职责清楚，统一字号、间距、圆角、边框、颜色与单色图标；主题使用 tokens。暗色基础保持，浅色作为同一套 tokens 的后续能力。

### 后续：形成运营闭环

增加运行概览与搬运记录，回答：现在有没有积压、哪个群/账号/平台失败、实际失败原因是什么。先做只读列表与详情。

当前有数据基础：`RedisJobStore.list(kind)` 可读记录（`utils/messagePipeline/redisJobStore.js:108`），交付任务存有平台、账号、群、状态、次数与时间（`utils/messagePipeline/mediaOutbox.js:125`），健康报告已有失败归并逻辑（`utils/messagePipeline/mediaRelayAdminReport.js:307`）。控制台尚无相应完整任务列表/状态 API，因此该阶段需要后端扩展。统计必须注明保留窗口、更新时间、结果是否完整；不能将 TTL 内留存记录当成永久累计。手动重试需独立动作契约，避免重复投递。

## 工程方案

建议建立独立前端工程，采用 Vue 3 + TypeScript + Vite，统一一套基础组件库（例如 Naive UI）并定制间距、颜色和密度。选择依据是配置表单和管理列表占比较高；框架选择不是验收目标，状态与配置契约才是。

建议边界：

```text
console/
  server.js             服务入口，保留独立 systemd 运行方式
  api/                  鉴权、配置、机器人、运行观测接口
  services/             YAML、备份、插件代理等服务
  frontend/
    src/app/            外壳、路由、导航元数据、错误处理
    src/components/     字段、保存栏、列表、弹层、状态呈现
    src/features/       pipeline / risk / persona / ai / bots 等
    src/lib/            API 客户端、字段适配、格式化
```

前端在开发/CI 构建，生产由现有 Node 服务提供静态产物，生产不运行 Vite。拆后端文件可分阶段完成，先抽出前端，避免一次同时迁移所有业务边界。

每页拥有独立的 baseline、draft、dirtyFields、loading、saving、requestId、editVersion，生命周期负责取消请求和清理轮询。保存固定页面与提交快照，响应只更新该快照的 baseline；后续编辑仍保留。401 由统一会话边界处理，已卸载页面不能被迟到响应重写。

配置字段继续来自现有 schema/服务端描述：前端新增展示分组与单位，不复制另一套默认值和范围。用显式组件注册表实现 Switch、Input、InputNumber、InputPassword、InputTextArea、GTags、GSubForm；未知类型不得静默降级。服务端负责相同约束及跨字段校验。

## 必须保留/补齐的契约

- 保留配置字段名与锅巴同源；保留 message.yaml 的定点更新、临时文件原子替换、修改前备份及最近 10 份保留。通用 schema 配置保留无变更不写入；AI 等其他保存路径后续补齐该能力。人设库是另一条存储路径，当前不具备相同的原子替换保证。新前端宜提交明确变化。
- 凭据 GET 返回已配置状态/掩码，不返回原文；写入明确保持、替换、清除，空白不自动当作清除。只改 input.type 不能完成这一项。响应和写入契约需协调发布或版本化，旧页面提交掩码/未编辑字段不得覆盖原凭据；回退旧前端也不得丢失凭据。
- 保存响应明确持久化结果；运行时确认能应用才显示已生效。逐字段给出即时应用/下一周期/重启等依据，对初始化配置核对并补齐应用路径。
- 保留 AI 渠道归一、优先级、fallback 和密钥保持语义；引入稳定渠道 ID，减少数组顺序变化导致错配的可能。
- 保留人设绑定优先级：群/私聊覆盖 → 账号默认 → 全局默认。
- 保留会话/令牌访问和 Yunzai 代理鉴权；iframe 迁移不破坏原入口。
- 对多管理员编辑增加版本冲突处理，避免较旧草稿覆盖他人已保存值。这是新增能力，当前尚未验证有并发写保护。
